## What you learned

This module was about the older docking standard: the Kubernetes `Ingress` API, served by Istio's arrival gate with no `Gateway` and no `VirtualService` anywhere.

**From [Claiming An Ingress](./course-01-claiming-an-ingress.md):**

- An `Ingress` is served only by the controller its class names. Use `spec.ingressClassName`; the older annotation `kubernetes.io/ingress.class` still works.
- The `IngressClass` for Istio needs `spec.controller: istio.io/ingress-controller`, exactly. That field cannot be changed: delete the class and create it again.
- An `Ingress` with no class shows `CLASS <none>`, is served by nothing, and produces no error. Here the gate gave `000`, because it had no orders for port `80` at all.
- Istio serves every `Ingress` through one gate: the Service `istio-ingressgateway` with pods labelled `istio: ingressgateway`, by default.

**From [Rules, Path Types And Translation](./course-02-rules-path-types-and-translation.md):**

- A rule names a host, paths, and one Service and port per path. There is no subset and no weight.
- `pathType: Prefix` compares whole pieces between `/` signs: `/anything/dock` matches `/anything/dock/7` but not `/anything/docking`. Istio's `uri.prefix` compares letters and would match it.
- `Exact` matches only the path itself. A path below it gets `404 NR` from the gate.
- Mission control translates the `Ingress` into the gate's route table. The `VIRTUAL SERVICE` column shows an `...-autogenerated-k8s-ingress` name, and no real `VirtualService` exists.
- There is no rule order: the most specific path wins.

**From [TLS And The Feature Ceiling](./course-03-tls-and-the-feature-ceiling.md):**

- `spec.tls` names the hosts and the TLS secret. The secret must be in `istio-system`, where the gate reads it.
- A secret next to the `Ingress` gives HTTPS `000`, HTTP still `200`, a `WARMING` secret on the gate and an `istiod` warning `secret istio-system/starfleet-credential not found`.
- Test HTTPS with `--resolve`, so curl sends the real host name in the TLS handshake.
- The `Ingress` API cannot express weights, mirroring, header matching, timeouts, retries, faults, subsets, gateway choice or rule order. Those need a `VirtualService` or the Gateway API.

## Check yourself

Try to answer each question before you open the answer.

<details>
<summary>1. You apply an <code>Ingress</code>, <code>kubectl apply</code> succeeds, and nothing answers. What do you check first?</summary>

The `CLASS` column of `kubectl get ingress`. `<none>`, or a class you do not recognise, means no controller serves the object. Then check that the `IngressClass` it names has `spec.controller: istio.io/ingress-controller`.
</details>

<details>
<summary>2. Your <code>IngressClass</code> has a typo in <code>spec.controller</code>. How do you fix it?</summary>

Delete the `IngressClass` and create it again with the right value. The field cannot be changed on an existing object; a patch is refused with `field is immutable`.
</details>

<details>
<summary>3. Which gate serves an <code>Ingress</code>, and how do you choose a different one?</summary>

The gate named by the mesh settings `ingressService` and `ingressSelector`: by default the Service `istio-ingressgateway` with pods labelled `istio: ingressgateway`. An `Ingress` has no field to choose another one.
</details>

<details>
<summary>4. A path has <code>pathType: Prefix</code> and <code>path: /api</code>. Which of <code>/api</code>, <code>/api/v1</code> and <code>/apis</code> match?</summary>

`/api` and `/api/v1`. `/apis` does not: `Prefix` compares whole pieces between `/` signs, and `apis` is not `api`.
</details>

<details>
<summary>5. You translate that <code>Ingress</code> path into a <code>VirtualService</code> with <code>uri: { prefix: /api }</code>. What changes?</summary>

`/apis` now matches too, because Istio's `uri.prefix` compares letters. For the same behaviour, use an `exact` match on `/api` and a `prefix` match on `/api/`.
</details>

<details>
<summary>6. You look for the <code>VirtualService</code> behind your <code>Ingress</code> and <code>kubectl get virtualservice</code> finds nothing. Is something wrong?</summary>

No. Mission control builds the gate's routes from the `Ingress` directly. The route table names an `...-autogenerated-k8s-ingress` object that exists only inside `istiod`.
</details>

<details>
<summary>7. HTTP works, HTTPS gives <code>000</code>, and the <code>Ingress</code> shows no error. What is the most likely cause?</summary>

The TLS secret is in the wrong namespace. It must be in `istio-system`, where the gate reads it. `istioctl proxy-config secret` on the gate shows it `WARMING`, and `istiod` logs `secret istio-system/<name> not found`.
</details>

<details>
<summary>8. A task asks you to send 10% of signals to <code>probe</code> v2 through the gate. Can you do it with an <code>Ingress</code>?</summary>

No. A path's backend is one Service with no weight. Use a `Gateway` with a `VirtualService` (weighted routes to subsets), or the Gateway API.
</details>

## Clean up the playground

Your playground is a whole Kubernetes cluster running on your machine. When you are done with this module, remove it, and any mission that is still running.

First, see what is still running:

```sh
astrona list
```

Remove the playground. The command takes its **name**, not its folder path:

```sh
astrona destroy ats-014-playground-060-02
```

If `astrona list` also showed a mission, remove it the same way, for example:

```sh
astrona destroy ats-014-lab-060-02-02
```

Then check that everything is gone:

```sh
astrona list
```

```text
No astrona labs running.
```

You can start the playground again at any time with the `astrona run` command from the module's landing page. It always starts clean, so nothing you broke carries over.

> *An `Ingress` needs a class Istio answers, means `Prefix` piece by piece, keeps its TLS secret on the gate's planet, and stops at host and path.*
