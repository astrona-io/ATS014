# Summary

A Kubernetes `Ingress` describes how requests from outside the cluster reach a Service inside it, and Istio's ingress gateway can serve it with no `Gateway` and no `VirtualService`. You learned that an `Ingress` does nothing until a controller takes it. Its `spec.ingressClassName` field, or the older `kubernetes.io/ingress.class` annotation, names an `IngressClass`. For Istio, that `IngressClass` must have `spec.controller: istio.io/ingress-controller`, exactly.

When the class is missing or names the wrong controller, Kubernetes still accepts the `Ingress` and reports no error. The gateway simply has no listener for it, so requests from outside get `000`. The `CLASS` column of `kubectl get ingress` and the `CONTROLLER` column of `kubectl get ingressclass` show the cause. You cannot edit `spec.controller` on an existing `IngressClass`; you delete the class and create it again.

Istio serves every `Ingress` through one gateway: by default the Service `istio-ingressgateway`, with pods labelled `istio: ingressgateway`. `istiod` translates each `Ingress` into ordinary gateway routes. The route table names an object that ends in `-autogenerated-k8s-ingress`, which exists only inside `istiod`, so `kubectl get virtualservice` finds nothing.

Path matching follows Kubernetes rules. `pathType: Prefix` compares whole elements between `/` signs, so `/anything/dock` matches `/anything/dock/7` but not `/anything/docking`. Istio's own `uri.prefix` compares characters and would match it. `Exact` matches only the path itself. A path with no rule gets `404` with the `NR` (no route) flag from the gateway, and the backend never sees the request.

For HTTPS, the `spec.tls` block names the hosts and a TLS secret. That secret must be in `istio-system`, because the gateway is the component that loads the certificate. A secret next to the `Ingress` leaves HTTP working and HTTPS failing, with a `WARMING` secret on the gateway and an `istiod` warning that the secret was not found.

Finally, an `Ingress` handles host, path and TLS, and nothing else. When a task needs weights, header matching, retries, timeouts, mirroring, faults or subsets, the answer is Istio's `Gateway` with a `VirtualService`, or the Gateway API.

Key facts:

- `IngressClass` controller for Istio: `istio.io/ingress-controller` (cannot be changed after creation).
- `Prefix` compares path elements; Istio `uri.prefix` compares characters.
- TLS secret for an `Ingress`: type `kubernetes.io/tls`, in `istio-system`.
- Test HTTPS with `curl --resolve` so the right name goes into the TLS handshake.
